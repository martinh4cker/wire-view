# WireView 有线副屏需求

已确认：用 Apple 芯片 Mac 和现有普通 Android 平板验证低延迟有线扩展显示。首轮允许开启 USB 调试和安装自制 APK，代码按可开源方向组织。

设计建议：先以 `adb reverse` 走 USB。Mac 用 VideoToolbox 编码 H.264，Android 用 MediaCodec 解码并显示到 Surface。先跑测试图，再验证 macOS 虚拟显示器与 ScreenCaptureKit 实时采集。若后续面向普通用户，单独验证无需 USB 调试的 AOA。

原型验收：

1. ADB 将平板识别为 USB 设备；视频服务仅监听回环地址。
2. 平板能持续解码和渲染 Mac 发来的测试画面，且日志能确认解码器及输出帧数；拔线会结束连接。
3. Mac 的显示器设置出现第二块屏，能把窗口拖过去，Android 端显示该屏画面。

待验证：其他 macOS 版本的虚拟显示与授权行为、实际端到端延迟和可用画质、其他平板的 USB 与解码器兼容性。首轮不设延迟达标结论，不包含触控、音频或正式发行。

首轮实测：macOS 26.6.1 和 Android 13，通过 ADB 回环转发经 USB 显示了真正的 Mac 扩展桌面。1920×1200 动态测试画面在平板端启用 MediaTek H.264 硬件解码，连续约 100 秒平均约 29 fps。主动断开 ADB 传输并重新设置转发后恢复播放。该设备的解码器没有声明低延迟模式；尚未测端到端延迟、物理拔插或 AOA。

第二轮已确认：连接时保留 Mac 原来的主显示器及现有屏幕排列，平板作为独立扩展屏追加到最右端。左侧 Dock 保持在原显示器。保持 1920×1200，动态内容目标 60 fps，不自动降到 30 fps；用平板实际渲染帧数验收。新增采集回调到平板渲染回执的计时，用于排查延迟；物理显示延迟仍需外部测量。触控待设计，第一版可将平板手势映射为副屏范围内的鼠标输入。

第二轮实测：Mac 主屏和外接屏的位置保持原样，平板从最左移到最右，左侧 Dock 的占用区域回到内屏。平板在持续变化的扩展桌面下约 60 fps。采集回调到平板渲染回执的中位数约 42 ms；Mac 编码阶段约 7 ms，平板收到完整视频帧到解码输出约 25–29 ms。未测面板像素实际亮起或触摸响应时间。

排列记忆：首次连接默认放在最右端。用户在 macOS「显示器 → 排列」手动拖动平板后，只记住平板与相邻显示器的相对位置；恢复时保留其他屏幕的位置和主屏。相邻显示器不在或目标冲突时先放到最右端，保留原记忆。

热插拔：Mac App 运行期间自动检测 USB 平板，拔线后重新插入自动恢复 ADB 转发并启动接收端，复用现有虚拟屏位置。当前不在拔线时移除虚拟屏；只在首次单台 USB 平板时选定设备，同一次运行不切换到其他设备，不覆盖端口已有的其他转发。2026-11-18 已通过断开及重新插线的实机测试：无需手动设置转发，平板自动恢复测试视频；用户确认画面恢复，日志确认 USB transport 改变后重新连接并持续渲染。

菜单栏设置（2026-11-18）：用户明确要求纯菜单栏，不弹设置窗口，也不展示大量信息。菜单用单选勾选提供尺寸、画质、帧率、屏幕，以及流畅/均衡/清晰预设。勾选后立即保存，显示中会自动重连视频会话以应用参数。屏幕可选扩展桌面，或镜像现有屏幕；镜像不改变物理显示器排列。开始/停止直接在菜单操作，屏幕排列、录屏权限和测试画面收在「更多」子菜单。默认不开启录屏；用户点开始后才请求授权。性能数据仅写日志，静态画面不要求重复发送。流畅 1280×800/60 fps/4 Mbps、均衡 1920×1200/60 fps/10 Mbps、清晰 2560×1600/60 fps/20 Mbps。低分辨率能减少编解码负载，实际改善需要目标平板实测。

多设备配置（2026-11-18，已确认）：菜单增加「安卓设备」，列出已授权的 USB 安卓设备及记住的设备，用勾选选择输出目标，一次只显示到一台。每台分别保存尺寸、画质、帧率、Mac 屏幕来源和排列位置。显示中改设置或切换设备自动重连，无须再次点开始；用户主动停止后改设置不擅自开始。选定设备拔插后继续等待同一台，不自动切到另一台。首次只有一台设备时自动选中，旧的全局配置迁移给首台；新增设备使用默认配置。设备身份只在本机保存序列号的 SHA-256 摘要和型号，不存原始序列号。各设备使用独立的 Mac 监听端口，避免旧平板重连到新目标的会话。尚待实测：同时连接两台真实平板、不同型号设备之间的切换；可用模拟 ADB 覆盖配置隔离及转发目标。

多设备配置验收：设备配置、来源与排列隔离、退出后重新加载、型号重名、USB 筛选、转发冲突和所选目标重插的新 transport 已有自动化测试。当前单台真实 USB 平板已通过纯菜单测试图验证：修改画质、尺寸、帧率均自动重连；切至虚拟的离线 B 后，A 无法进入 B 的端口；切回 A 自动恢复它自己的设置和视频；主动停止后调整画质不自动开始。测试不采集桌面，同时两台真实设备及新版真实桌面采集仍未重新验证。

开源整理（2026-11-18，已确认）：将当前项目建立为独立本地 Git 仓库，使用 MIT 许可证，补齐使用、构建、测试、架构协议、贡献及安全说明，提供本地 Makefile 和 Issue/PR 模板。构建产物、日志、调试签名和本机配置排除在 Git 之外。此次不创建 commit、不暂存文件、不创建远程仓库，也不上传或发布。

开源整理验证：从 Git 待收录文件复制出不含原 `.build/` 的干净源码副本，Mac 构建及全部默认自动化测试通过；文档链接、Issue 模板 YAML、Shell 语法与 Git 忽略项检查通过。Android 本轮重编译在前置环境检查处停止：当前环境未提供 SDK Platform 35 与 Build-Tools 35.0.0，未重新确认 APK 构建。保留此前的实机记录，不将本轮环境检查当作 Android 构建通过。

高帧率（2026-11-18，已确认）：菜单增加 90、120 帧，按设备保存并沿用显示中自动重连；默认及预设保持 60。设置统一验证 30/60/90/120，虚拟模式、编码器、协议头和测试图定时均沿用目标值，原接收端协议上限已为 120。90/120 为实验选项，不宣称目标即为实测帧率。已覆盖菜单勾选、配置重载和设备间隔离；实际 90/120 fps 及对应桌面刷新仍待验收。

高帧率短时实测：1280×800/4 Mbps 测试图的 90 fps 目标，Android 回调统计约 86–91 fps，Mac 回执延迟中位约 37 ms；120 fps 目标下，Android 回调仍约 89–93 fps，而回执延迟中位升至约 481 ms。120 档存在吞吐不足及积压的迹象，当前不建议用它解决 60 档的卡顿；这不是物理呈现帧率或面板延迟的测量，也未确定瓶颈位于解码器、调度还是显示端。新增 `--video --high-fps` 测试入口，使用生成画面，不采集桌面。

流畅度排查：当前 1280×800/4 Mbps/60 fps 下，持续运动测试的 Android 渲染回调日志曾连续报告约 60 fps，但 SurfaceFlinger 视频层采样出现约 33.3 ms 的呈现间隔、50 ms 的长间隔，面板扫描周期为 16.7 ms。两个统计的时间窗口与计数语义不同，不能仅凭回调计数断定实际满帧，也尚未确定是采集/编码掉帧、解码调度还是显示合成造成。后续需对齐持续运动期间的采集、编码、解码与实际呈现时间，再做性能改动。暂未因这一样本改动安卓端或降低用户画质。

补充对齐验证：90/120 目标的动态测试中，分别确认 SurfaceFlinger 呈现历史在采样期间向前推进约 4.8/4.2 秒，排除读取完全停滞的旧历史；两档采样呈现间隔中位仍约 33.3 ms，面板扫描周期仍为 16.7 ms。120 的第二次回执延迟中位约 627 ms。高目标的会话建立、参数保存、自动重连和停止测试通过；面板模式未切至 120 Hz，实际高刷显示仍未达标。不能将解码渲染回调数等同于用户看到的帧数，接下来应检查安卓显示调度和帧率请求的生效情况。

显示调度修复（2026-11-18）：用户要求调查实际低帧率。对照确认平板本机动画实际约 60 fps，用户确认明显顺滑；视频流同时存在 TCP 确认等待抖动及此设备上的直接视频呈现限制。接收端增加逐包 `TCP_QUICKACK`（不支持则回退）、显式解码帧率及实时负载声明，使用 SurfaceTexture 外部纹理与 EGL/GLSurfaceView 合成替代原视频直出。动态期间保持显示节奏，静态时停止重复 GPU 绘制；暂停和恢复时重建纹理与接收连接。保持原画质，不增加固定抖动缓冲，不改变平板全局网络或系统安全设置。

修复验收：1280×800/4 Mbps/60 fps 测试图的接收间隔 p95 从约 44 ms 降至约 19 ms；系统呈现从约 30 fps 提至约 60 fps，稳态及两轮前后台恢复的呈现间隔中位约 16.67 ms，p95 约 16.69 ms。新纹理更新约 58–60 fps；历史记录中的“60 fps”若仅依据解码回调，不能作为实际呈现达标证据。本轮已恢复 Android SDK 构建工具并成功构建、覆盖安装 APK，Mac 默认测试通过。真实桌面及其他设备仍需验收；不提交 commit、不暂存或上传。[完整排查记录](performance.md)

多语言与版本（2026-11-18，已实现）：Mac 菜单栏与 Android 接收页支持简体中文和英文，分别跟随各自系统语言；其他语言显示英文。版本保持 0.1.0，Mac 和 Android 使用一致的版本名。

品牌图标（2026-11-18，已实现）：Mac App 与 Android 启动器共用两台重叠屏幕及简化 USB 线缆标志，背景为铺满画布的纯深蓝色；构建时生成 Mac `.icns` 和 Android 多密度启动图标。Mac 菜单栏保留原生双屏符号。


触摸控制：首版在扩展桌面中实现绝对坐标点击、单指拖拽和双指滚动，默认启用，菜单不提供开关。需要 macOS 辅助功能权限，等待授权时画面仍可播放。待实机验收包括四角定位、改变排列后定位、双指滚动和拖动时拔线释放。


连接生命周期调整：拔线、目标 transport 更换或持续无法建立视频连接时，停止共享并移除虚拟屏。重插后手动开始，保留设备配置和排列。同一 USB transport 上接收端短暂重启时可在限时窗口内恢复。此行为取代历史记录中的「拔线保留虚拟屏并自动恢复」。


多指系统手势：保留单指点击、拖拽和双指滚动。三指左右切换桌面，上下打开调度中心和当前 App 窗口；四指左右切换 App。使用 macOS 系统快捷键，触摸会话沿用现有 USB 认证机制。

安卓亮屏：接收页在前台且开始呈现本次会话的画面后才请求保持亮屏。等待连接、断连、渲染失败或页面进入后台时，交由 Android 的系统熄屏设置管理。

安卓等待页：启动后用纯黑底显示「等待连接」，播放中断后用纯黑底显示「已断开连接」，遮住上一帧。接收端重试期间保留提示，收到新的视频帧后恢复画面。
